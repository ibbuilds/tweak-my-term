# tweak-my-term: plan

Status (2026-11-23): M0-M8 verified locally (198 tests, catalog check, privacy scan).
Added since: layout as its own axis (inspire `--layout`, look `layout.arrangement` drawn in
the preview and built per tool), a design guide distilled from real rices, and a
window-manager catalog for all three OSes (AeroSpace, yabai, GlazeWM, Hyprland,
sway, i3, niri).
Changed after review: no presets. The repo ships knowledge (design guide, catalog,
inspiration from real rices, composition-aware tooling), never a terminal to copy; every
terminal is built for its user. Background treatment reads the composition instead of
darkening by default. Open: git history still holds the author's personal setup and
derived art from the first commits; rewrite it (with the author's go-ahead) before the
first push. No release until the "done" checks at the end pass.

## 1. Goal

One request ("make my terminal look like this", "something dark and calm, fast", "I don't
know, show me") and the user's agent delivers the finished terminal on **Windows, macOS
or Linux**, first time. The terminal is: the style, the colors, the font, the layout, the
visual anchor (image, video, ASCII art), the polish, and the tools. tweak-my-term gives the
agent everything that takes: inspiration, design method, asset tooling, per-tool
knowledge, and a safe way to apply it. It also works for a person with no AI.

It combines existing tools (terminals, shells, prompts, fonts, palettes, CLI tools). Its
own code is glue: design tooling, an apply engine with gates, and knowledge.

No two terminals are the same, so the repo holds no looks to copy (no presets, no
author's setup). What it gives the agent is the difference between an ordinary terminal
and a great one: a design guide distilled from real rices, a search over thousands of
them that the agent looks at (screenshots, judged by the terminal window inside), and
tools that adapt to each composition (palette from the anchor, readability fixes only
where text needs them).

## 2. How a terminal gets built (the pipeline)

Every request goes through the same stages. The skill drives them; the toolkit and the
engine do the work that has to be exact.

| # | Stage | Output | Who |
|---|---|---|---|
| 1 | **Detect** | `detect.json`: OS, terminals, shells, prompt tools, fonts, CLI tools, versions, existing configs, current startup times | engine |
| 2 | **Brief** | `brief.md`: what the user wants, in their words + constraints (OS, terminal, shells, speed budget, must-keep habits) | agent interview |
| 3 | **Inspire** (when the user is vague or wants options) | 3–6 candidates with screenshot links, tools used, dotfiles repo | toolkit `inspire` + agent |
| 4 | **Anchor** | `anchor.png` (or `.gif`/shader): the one visual that defines the style | user file/URL, a rice screenshot, or generated by the toolkit |
| 5 | **Style** | design tokens: 16 ANSI colors + bg/fg/cursor/selection/accent, font, density, layout, effects | toolkit `palette` + `contrast` + agent judgment |
| 6 | **Look spec** | `look.json` (schema-checked, tool-neutral) | agent |
| 7 | **Fit** | which tools on this OS deliver each part of the spec; what can't be done and the closest alternative | catalog `capabilities.json` + agent |
| 8 | **Preview** | `preview.html` (mock terminal with the real palette, font, background, prompt) + `swatch.png` | toolkit; user approves the look before anything touches the machine |
| 9 | **Render** | native config files + generated assets, staged inside the run folder | agent with catalog recipes; toolkit for assets |
| 10 | **Plan → approve → apply** | backups, diff, writes, installs | engine (gated) |
| 11 | **Verify** | each tool's own config check, each shell starts and draws a prompt | engine |
| 12 | **Measure** | shell startup before/after against the budget | engine |
| 13 | **Polish** | screenshot of the real terminal → agent compares with anchor/preview → small fixes → re-apply | engine `shot` + agent |
| — | **Restore** | byte-for-byte undo of any run | engine |

### The visual anchor (stage 4)

A terminal style starts from one visual. Sources, in the order the skill offers them:
1. **The user's own** image, GIF, video still or screenshot (file or URL).
2. **A rice** picked in Inspire: its screenshot is the anchor, its dotfiles are the
   reference configs.
3. **Generated** by the toolkit, no external service needed:
   - a parametric scene (sky/moon/horizon/terrain, gradients, noise fields, grids, waves,
     stars) painted in the chosen palette;
   - custom art: the agent writes a small paint script against the toolkit's raster API
     (shapes, gradients, noise, blur, glow), as `scene.js` does today;
   - ASCII/ANSI art from any image (logo, dossier, fetch art).
4. **An image tool the user already has** (an image-generation MCP or app): accepted as
   input like any user image.

Treatments turn an anchor into a background that keeps text readable: dim, blur, vignette,
bloom, pixelate, quantize to the palette, ASCII-glyph overlay, scanlines. Animated
anchors only go to terminals that support them (GIF backgrounds, custom shaders); the
capability matrix decides.

### Style from the anchor (stage 5)

- `palette`: extracts dominant colors (median cut in OKLab), then assigns them to ANSI
  slots by hue, filling missing hues by rotating at the anchor's lightness and chroma.
  It produces a full 16-color scheme + bg/fg/cursor/selection that matches the image.
- `contrast`: WCAG ratios for fg on bg, each ANSI color on bg, and text over the
  background image's real luminance. It fixes failures by shifting lightness only, so
  hues stay.
- Fonts: the catalog describes each Nerd Font (style, width, ligatures, x-height) so the
  agent can match "feel" to the anchor and install it per user.
- Layout: padding, tab bar, splits/panes, multiplexer layout, prompt structure (lines,
  segments, density), fetch/dossier on start.

### Inspiration (stage 3)

- **Rices**: the dataset behind dotfiles.lol (`0xN1nja/awesome-dotfiles`, MIT, 4,130
  r/unixporn setups, each linked to its GitHub dotfiles; terminals kitty 800, Alacritty 708,
  st 315, urxvt 243, foot 110, Ghostty 63, iTerm2 58, WezTerm 44; zsh 510, fish 208).
  `inspire` searches it by terminal, shell, colorscheme, WM, distro and keyword, ranked by
  score. It reads the JSON from GitHub (cached), never scrapes the site.
- The agent **looks at** the screenshots it shortlists (vision), finds the terminal
  window in each desktop shot, and judges layout, composition, palette, type and prompt
  against `skills/setup/references/design.md`. Results are varied by design (no repeated
  scheme, WM or author; seeded random draws), so each run sees different examples.
- **Palette galleries**: iTerm2-Color-Schemes, tinted-theming/base16, Catppuccin, and so on.
- For a chosen rice, the agent opens its screenshot (vision) and its dotfiles repo, and
  pulls the terminal-related files (`kitty.conf`, `alacritty.toml`, `.zshrc`,
  `starship.toml`, `tmux.conf`...) as reference.
- Rules: link to screenshots, never re-host them; other people's configs are used for the
  user's machine, not copied into this repo unless their license allows it.

### Scope

Everything inside the terminal window: emulator, font, colors, transparency/blur,
background image/animation, shader, padding, cursor, tabs/splits, shell, prompt, line
editing, multiplexer, fetch/dossier, TUI and CLI tools and their themes. Desktop ricing
(window managers, bars, wallpaper) is out of scope, but its palette/font/terminal configs
are used.

There is no limit on what a user can ask for. Tools with a **verified recipe** are built
fast and right first time. For any other tool the agent reads its docs live, marks it
"unverified" in the run, and it still goes through backup, check, measure and undo.
Frequently requested tools get recipes over time.

## 3. Architecture

| Part | What | Runs on |
|---|---|---|
| `engine/` (`tmt`) | Run state machine with gates, detect, stage/plan/approve/apply/verify/measure/restore, screenshots, Claude Code hook handlers | Node ≥ 20, zero npm dependencies, Windows/macOS/Linux |
| `kit/` (`tmt art`, `tmt inspire`...) | PNG codec, palette, contrast, treatments, scene painter, ASCII art, preview, rice search | same |
| `catalog/` | One folder per tool: `tool.json` (OSes, install ids, config paths, validator, startup cost, verified date) + `recipes/*.md` (how to do each capability in that tool) | data |
| `guides/` | Design method (anchor → palette → font → layout → polish), readability, performance, per-OS gotchas | data |
| `skills/tweak-my-term/` | `SKILL.md` (the pipeline) + stage references | any agent with Agent Skills |
| Plugin (`.claude-plugin/`, `hooks/`, `agents/`, `bin/`) | Commands, hooks, subagents, `userConfig` | Claude Code |

**Why Node, not PowerShell + POSIX sh:** one implementation and one test suite on all
three OSes, real JSON/JSONC handling, precise timing, and the art code is already Node.
The tradeoff is that Node must be installed. The bootstrap shims (`bin/tmt`,
`bin/tmt.cmd`) detect a missing Node, print the exact install command for that OS, and
stop; the agent asks the user before installing it. Nothing else is required; the
optional tools (hyperfine, chafa, ImageMagick) only make things faster or nicer.

**Why not MCP:** the engine + hooks enforce order without a server process, and the skill
works in every agent. Revisit only for agents that can't run commands.

### The run and its gates

`~/.tweak-my-term/runs/<id>/`: `state.json`, `detect.json`, `brief.md`, `look.json`,
`anchor.*`, `preview.html`, `staged/` (proposed files), `plan.json`, `backup/`,
`manifest.json`, `measure-before.json`, `measure-after.json`, `shots/`.

```
new -> detect -> (brief/inspire/anchor/style/look/preview: agent + kit, files in the run)
    -> stage* -> plan -> approve -> apply -> verify -> measure -> done
                                       \-> restore (any time after apply)
```

| Command | Gate |
|---|---|
| `tmt new` | refuses if another run is applied but not finished, unless `--force` |
| `tmt stage write <target> <file>` / `stage block <target> <file>` / `stage merge-json <target> <fragment>` / `stage install <manager> <id>` / `stage font <name>` / `stage check <cmd...>` | target must be under the user's home (or a known config path); `look.json` must be valid |
| `tmt plan` | something staged; prints the full diff and install list; computes the plan hash |
| `tmt approve <hash>` | hash matches the current plan |
| `tmt apply` | approved; no target changed since `plan`; backs up every target first; installs only if `allow_installs` |
| `tmt verify` | runs every check; any failure → state `failed`, with the output |
| `tmt measure` | records timings; over budget → warning + pointer to the guide |
| `tmt restore [run]` | restores byte-for-byte from the manifest, removes files that didn't exist before |
| `tmt status` | prints the next required step (used by hooks and agents) |

Write kinds:
- `write`: replaces the whole file.
- `block`: inserts or replaces a managed block (`# >>> tweak-my-term >>>`) in rc files, so
  the rest of the user's `.bashrc`/`.zshrc`/`$PROFILE` stays as it is.
- `merge-json`: key-level merge for JSONC configs (Windows Terminal): lists matched by
  `name`/`guid`. Comments in changed keys may be lost; the backup keeps the original.

`TMT_HOME` (tests) redirects every target to a fake home, so tests never touch the real
machine.

### Claude Code plugin

- `bin/tmt`, `bin/tmt.cmd`: shims, so the agent calls `tmt` directly.
- Skills (slash commands): `/tweak-my-term:setup` (full pipeline), `:inspire`,
  `:capture` (read the current setup into a look), `:doctor` (read-only diagnosis),
  `:restore`, `:status`.
- Subagents: `inspiration-scout` (searches rices, opens repos, returns candidates
  without flooding context), `terminal-auditor` (detect/measure/diagnosis).
- Hooks (all run `node engine/hook.js <event>`, so one code path on every OS):
  - `PreToolUse` (Write/Edit/Bash/PowerShell): denies direct edits to live config files
    (paths from the catalog + targets of the current run), with "stage it with `tmt`".
  - `Stop`: while a run is applied but not verified and measured, blocks the stop with
    the next command. Respects `stop_hook_active` so it can't loop.
  - `SessionStart`: if a run is open, adds its status to context.
- `userConfig`: `startup_budget_ms`, `allow_installs`, `package_manager`.

## 5c. Roadmap to "any terminal from words" (2026-11-23)

Goal: a user tells their agent "make me a vaporwave, aesthetically pleasing terminal" (or
any mood, image, rice or layout) and gets the whole terminal: anchor art, background,
palette, font, prompt, layout, themed tools and features, built for their OS and
terminal. When the request leaves something open that changes the result, the agent asks
(through the user's agent, with options), then builds. Proven by graded rehearsals, not
by "the configs parse".

What already works (rounds r1/r2, 9 agent runs): request → plan with correct configs for
Windows Terminal, WezTerm, kitty, alacritty, Ghostty, tmux, zellij, fish, starship, btop,
cava, yazi, helix; apply/verify/restore. What is unproven: the conversation (every run was

## 6. Risks

- **Plugin mechanics on Windows** (M0). Fallback: call `node` with the full path.
- **No Linux/macOS machine here** (no WSL distro, no Docker): CI covers logic; visual checks
  need a real machine.
- **Recipes go stale**: every fact has a verified date; CI flags facts older than 6 months.
- **Inspiration data changes**: pin a commit; anchors from files and URLs still work.
- **JPEG input**: the kit decodes PNG/BMP/GIF; JPEG/WebP are converted with OS tools
  (PowerShell System.Drawing, `sips`, ImageMagick/ffmpeg) when present.

## 7. Rules

- No personal data (username, PC name, email, local paths) in the repo.
- No third-party or derived art; generated art only. No presets or personal setups. Other people's screenshots are linked, never
  re-hosted.
- Commit as `ibbuilds <70708615+ibbuilds@users.noreply.github.com>`.
- Nothing installs or writes by itself: stage, show, approve, back up.

## 8. Dependencies

- Runtime: **Node ≥ 20**, no npm packages. Optional: hyperfine (timing), chafa
  (terminal image preview), ImageMagick (more image formats).
- Dev: none beyond Node (`node:test`). CI uses GitHub's runners.
